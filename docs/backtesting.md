# Hyperliquid Perpetual SAR backtest contract

This document defines the first offline backtest supported by this repository.
It is deliberately narrower than the live runtime so that every reported result
has an explicit data, timing, and execution contract.

## Scope

The first release replays the current Hyperliquid USDC perpetual SAR strategy:

- entries generated by `SARChecker` after the configured consecutive SAR run;
- at most one position for the tested symbol;
- a position is closed after the configured number of consecutive opposite SAR
  directions;
- take-profit and stop-loss trigger prices use the configured ROE divided by
  the position leverage, matching `ProtectionReconciler`;
- the existing parabolic trailing-stop state transition is replayed at a
  configured interval; and
- market entry, signal close, protective exit, fees, slippage, and optional
  funding are included in the trade ledger.

Spot strategies, multiple simultaneous symbols, liquidation modelling, order
book depth, partial fills, and latency distributions are outside the first
release. The engine must not connect to an exchange, read API credentials, or
submit an order.

## Input series identity

Every input series is identified by all of these fields:

- exchange (`hyperliquid` for the initial target);
- market type (`perpetual`);
- normalized symbol (for example `ETH/USDC:USDC`);
- timeframe; and
- UTC candle-open timestamp.

Mixing rows with a different identity is invalid. A timestamp alone is not a
sufficient database key because spot/perpetual and 1-minute/30-minute rows can
share it.

The offline CSV contract requires `timestamp`, `open`, `high`, `low`, `close`,
and `volume`. `funding_rate` is optional. Timestamps are candle-open times and
must be unique, strictly increasing, UTC-normalizable, and separated by exactly
the declared source timeframe. Prices must be finite and positive, volume must
be finite and non-negative, and OHLC bounds must be internally consistent.

When a higher timeframe is derived from a lower timeframe, it is aggregated as
open=first, high=max, low=min, close=last, and volume=sum. Incomplete buckets,
gaps, duplicates, and a trailing partial candle fail closed. Selecting only the
lower-timeframe rows that happen to lie on a higher-timeframe boundary is not
aggregation and is forbidden.

## Event timing and look-ahead prevention

The engine operates on a lower execution timeframe, normally 1 minute, and
derives the configured signal timeframe, normally 30 minutes.

For each execution candle, the event order is:

1. execute an action queued by the previously closed signal candle at the
   current execution candle's open;
2. evaluate fixed or trailing protective triggers using this execution
   candle's high and low;
3. apply funding supplied for this timestamp and record close-marked equity;
4. update trailing state at a configured boundary using the execution candle's
   close; and
5. if a signal candle has just fully closed, evaluate SAR using only signal
   candles available at that point and queue any action for the next execution
   candle open.

An entry or signal close therefore never fills at the close that generated its
signal. The default fill is the next execution candle open with adverse
slippage. If no next candle exists, the queued action is not filled.

## Execution assumptions

- Entry notional is fixed in quote currency and quantity is not rounded to an
  exchange lot size in the first release.
- Market fills use configurable adverse slippage in basis points.
- Entry and exit use a configurable taker-fee rate. Fees are charged on fill
  notional.
- A positive funding rate means a long pays and a short receives. Missing
  `funding_rate` data is treated as zero and the report states that funding was
  omitted.
- ROE protection is converted to a price distance with
  `roe_percent / 100 / leverage`, matching the live protection calculation.
- If the execution candle opens beyond a stop, the stop fills at the worse open
  before slippage. A take-profit remains capped at its trigger before slippage.
- If stop-loss and take-profit are both reachable in the same execution candle,
  stop-loss wins. This conservative rule avoids inventing an unknown intrabar
  path.
- Opposite-SAR close is queued for the next execution open. It does not reverse
  in the same event; a later valid entry signal is required while flat.

## Trailing-stop approximation

The live runtime samples a ticker at the configured trailing interval. The
backtest samples the close of the execution candle ending on that interval.
An execution timeframe must evenly divide the trailing interval. A newly
activated trailing stop moves to at least break-even and becomes effective for
the next execution candle. Later interval samples reuse the existing
`TrailingStopManagerHyperLiquid` update formula. This is a deterministic
approximation, not tick-accurate replay.

## End of data and outputs

By default an open position is closed at the final execution candle close with
adverse slippage and fees, using exit reason `end_of_data`. This produces a
fully realized and comparable result. Reports contain:

- a JSON summary with input identity, configuration, funding availability,
  total net PnL, total return, maximum drawdown, win rate, profit factor, trade
  count, and final equity;
- a CSV trade ledger with entry/exit times and prices, side, quantity, gross
  PnL, entry/exit fees, funding, net PnL, and exit reason; and
- a CSV equity curve marked at each execution candle close.

Identical validated input and configuration must produce byte-equivalent
summary values and deterministic ledger/equity rows.

## Running the backtest

After `uv sync`, run the offline CLI with an explicit fee assumption:

```bash
uv run backtest \
  --input historical_data/hyperliquid-eth-perp-1m.csv \
  --symbol ETH/USDC:USDC \
  --source-timeframe 1m \
  --signal-timeframe 30m \
  --start 2026-01-01T00:00:00Z \
  --end 2026-07-01T00:00:00Z \
  --leverage 3 \
  --order-notional 12 \
  --taker-fee-bps <current-taker-fee-bps> \
  --slippage-bps 1 \
  --output-dir backtest_results/eth-30m
```

The fee is required instead of silently embedding an exchange fee that can
change. Standard CSV uses the required columns defined above. Raw Binance kline
CSV can be read with `--csv-format binance_klines`, but the initial engine
intentionally rejects non-Hyperliquid or non-perpetual identity. Successful
execution writes `summary.json`, `trades.csv`, and `equity.csv` beneath the
output directory.

## Required verification

Automated tests must cover data identity and validation, correct OHLCV
aggregation, incomplete buckets, exact closed-candle signal timing, next-open
fills, adverse slippage and fees, long/short TP and SL, same-candle TP/SL
collision, opposite-SAR close, trailing activation/update, optional funding,
end-of-data close, metrics, and deterministic CLI artifacts.
